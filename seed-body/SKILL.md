# Seed Body — 대화로 Essential 몸체 심기

코드가 없는 출발점에서 `사용자 발화 → Essential 흐름 → Domain harvest → UseCase 재기술`
순서로 v1 몸체를 만든다. 결정 대상은 둘뿐이다 — **v1 Essential UseCase 집합**과 **그 집합을
말할 Essential Domain 언어**. 산출물 `ESSENTIAL_DOMAIN.md`·`ESSENTIAL_USECASE.md`가 후속
System 도출, PRD, 티켓, 구현, 검증의 공용 계약이 된다. 구현 수단 선택과 System 설계는
후속 단계의 몫이다.

이 규칙들을 바꾸기 전에 `DESIGN.md`를 읽는다. 소유 지도와 편집 게이트가 거기 있다.

## 정체성 원칙

이 목록은 동결이다. 스크립트 게이트가 아니라 판단 지침이며, 원칙 추가 — 의미상 의무를
늘리는 재표현 포함 — 는 사용자 비준을 요구한다.

1. **발화 근거** — 캐노니컬의 모든 주장은 사용자 턴 참조와 짧은 직접 인용에 결박된다.
   LLM 유추는 `[가정]` 후보로만 제안하고, 사용자가 비준한 턴부터 근거가 된다.
2. **Essential admission** — Essential은 서비스가 제공하고자 하는 것 자체를 표현하는
   층이다. v1 Essential 집합은 핵심 행위자가 흐름에 진입하는 지점부터 핵심 가치가 성립하는
   지점까지를 Essential 문장만으로 서술할 수 있어야 한다. 개별 조각은 표현에 기술어가
   있는지가 아니라 사용자가 요구하는 의미로 판정한다. 의도·책임·관측 가능한 결과·정책·품질
   제약은 Essential이고, 사용자가 그 결과를 달성하는 방법으로 말한 실행 수단만 원문 그대로
   파킹한다. 애매하면 `[층미분류]`로 두고 한 번 확인한다.
3. **Harvest 후행** — Domain을 선행 열거하지 않는다. Essential 흐름 코퍼스가 쌓인 뒤
   재발·공기 또는 load-bearing 싱글턴에서 수확하고, 사용자의 사용 이력으로 이름을 수렴한다.
4. **비전 보존과 v1 수렴** — 큰 비전은 보존하되, 처음 구현해 핵심 가치가 성립하는 최소
   흐름을 v1로 제안한다. 사용자가 명시적으로 승인한 v1 밖 Essential만 LATER에 둔다.
5. **Breadth-first** — 한 턴에 가장 값진 질문 하나만 묻고 같은 슬롯에 연속으로 매달리지
   않는다. 카테고리 프라이어는 bounded 위험순 질문 재료이며, 정답이나 Evidence가 아니다.
6. **사람 비준이 유일한 진실원천** — 메타 기준(CRITERIA)과 전체 내용의 2단계 비준을 통과한
   것만 캐노니컬로 승급한다. 필수 질문이 확정 내용으로 답을 가질 때만 종료 후보가 된다.

## 파일

작업 상태 — 흐름 코퍼스, 파킹, 프라이어, 수확 리포트, 후보 큐, LATER, QUESTIONS, CRITERIA,
REJECTED — 는 `.scratch/seed-body/`에 대화에 맞는 자유 형식으로 유지한다. 스키마는 없고,
눌러앉는다고 캐노니컬이 되지 않는다. Evidence 줄과 `EF-nnn`/`SF-nnn` id, `{term}` 마킹의
예시는 [references/artifacts.md](references/artifacts.md)에 있다. 워크스페이스가 없으면 같은
상태를 대화 안에서 유지하고, 대화가 길어지면 파일 저장을 제안한다.

승급 시 대상 프로젝트 `docs/`에 인계 패키지를 materialize한다 — 경로·포맷·핵심/고정 인계/
선택 감사 구분은 artifacts.md가 소유한다.

## 발산 — 턴 처리

발산 국면에서는 사용자가 편하게 말하게 두고 정리 부담은 에이전트가 진다. 매 턴 이 순서를
지킨다.

1. **발화 근거 고정** — 새 발화의 턴 번호(`T{n}`)와 짧은 직접 인용을 먼저 잡는다. 아직
   코퍼스에 쓰지 않는다.
2. **Essential admission** — 정체성 원칙 2로 판정한다. 시간·복구·가용성 표현도 사용자가 그
   자체를 성공 조건으로 요구하면 Essential이고, 재시도·재접속 같은 동작도 방법으로 말했으면
   파킹이다. 파킹 조각은 System/Implementation으로 더 분류하거나 타당성을 판정하지 않는다.
   혼합 발화는 분리를 문장으로 제안해 한 번 비준받는다 — "푸시로 5초 안에 공지가 떠야 해"는
   `공지가 5초 안에 보인다`가 성공 조건인지 먼저 확인하고, 맞으면 그것만 Essential로 두고
   `푸시`를 파킹한다.
3. **되비춤과 기록** — admission이 끝난 Essential 조각만 `[행위자]가 [상황/트리거]일 때
   [하려는 것] → [기대 결과]` 문장으로 되비춘다. 사용자 vocabulary를 유지하고 후보 용어를
   `{term}`으로 마킹해 코퍼스에 `EF-nnn`으로 누적한다. 파킹 조각은 `SF-nnn`으로 기록하고
   받치는 `EF-nnn`을 `Trace:`로 단다. 받치는 Essential이 아직 없으면 파킹하지 않고
   `[층미분류]`로 유지한다.
4. **v1 경계** — v1 밖으로 보이는 Essential은 "이건 v1 다음으로 미뤄둘까?"라고 확인한다.
   승인되면 LATER로, v1 코어라면 코퍼스에 둔다.
5. **승격 체크** — 이번 턴의 LATER 항목이 v1 뼈대의 빈 슬롯을 가리키면 "이건 사실 v1 코어
   아닐까?"를 한 번만 확인한다. YES면 코퍼스로 되돌리고 NO면 그대로 둔다.
6. **회전** — 종료 임박 신호가 없으면 가장 값진 빈/약한 슬롯 하나만 질문한다. 후보 슬롯:
   흐름 빈칸, 역방향·예외, 복수 행위자의 권한 충돌, 위험한 외부 약속, 프라이어 미처분 항목.
   v1 코어 UseCase마다 역방향·예외를 한 번은 질문하거나 명시적 `해당 없음`·유보·v1 밖으로
   처분한다.

작업 라벨은 `[가정]`(비준 대기 유추), `[충돌]`(같은 개념 두 용어 — 사용 이력으로 수렴 제안),
`[층미분류]`(admission 대기) 셋뿐이고 항목당 0~1개다. 사용자가 직접 말했거나 승인한 항목은
라벨 없이 비준 대기에 합류한다. 발산 중 Domain은 `{term}` 마킹으로만 유지한다 — Domain 후보
생성과 재기술은 종료 게이트의 harvest에서 한 번 수행한다.

### 카테고리 프라이어

서비스 카테고리를 식별할 수 있을 때 프라이어 목록을 만든다. 한 run에 최대 7개, "빠뜨리면
v1 핵심 가치·신뢰·안전이 깨질 가능성"이 큰 Essential 빈틈만 다음 순서로 고른다.

1. 핵심 가치가 전달되는 주 흐름
2. 실패·취소·되돌림처럼 비가역 결과를 막는 흐름
3. 같은 대상을 다루는 행위자의 권한·충돌
4. 외부 사람·기관과의 약속, 신뢰·안전 위험

기능 동등성 체크리스트와 구현 관심사는 제외한다. LLM 지식과 웹 근거는 질문을 고르는 데만
쓴다. 카테고리 이해가 바뀌면 항목을 추가하지 말고 아직 묻지 않은 낮은 위험 항목을 교체한다.
각 항목은 답(`EF-nnn`) / 해당 없음(사용자 확인 턴) / 유보(QUESTIONS) / v1 밖(승인 후 LATER)
중 하나로 처분될 때까지 회전 풀에 남되, 같은 항목을 두 번 연속 묻지 않는다. 점검표를
읽어주지 말고 구체 시나리오로 질문한다. 프라이어는 승급되지 않고 종료 시 이동하지 않으며,
미처분 항목은 CRITERIA 필수 질문으로 승계한다.

### 질문 처분

빈칸이나 모호함은 셋 중 하나로 처리한다 — 유추 가능하면 구체 제안값을 `[가정]`으로 큐잉해
"이렇게 보면 맞아?"라고 한 번 묻고, 사용자가 답할 수 있으면 한 번에 하나만 묻고, 지금
결정하지 않기로 하면 유보를 QUESTIONS에 기록하고 회전한다. 단 하나 남은 필수 질문이면 그
사실을 짧게 밝히고 닫는다. 현재 질문과 무관한 응답을 억지로 Evidence에 연결하지 않는다 —
새 Essential 아이디어면 admission과 v1 확인을 거치고, 단순 여담이면 대화에만 남긴다.

### 종료 임박 휴리스틱

다음 중 하나면 수렴으로 들어간다. 게이트 진입은 종료가 아니라 수렴 시작이며, CRITERIA가
미답을 발견하면 다시 한 질문씩 회전한다.

1. **명시 신호** — "다 말한 듯", "다음 단계는?", PRD·프로토타입 등 downstream 요청
2. **대화 정체** — 새 조각 없는 회전 2턴 이상 또는 응답 고갈; "v1 코어에 더 보탤 게
   있어?"를 한 번 확인한 뒤 진입
3. **자기 완결성** — 실제 용어로 "누가 어떤 흐름을 통해 어떤 가치를 얻는가"를 placeholder
   없이 쓸 수 있음; 조용히 게이트로 들어가 메타 비준을 제시하고, 사용자가 부정하면 회전으로
   복귀

## 수렴 — 종료 게이트

고정 순서: **정합성 스캔 → harvest와 재기술 → CRITERIA → 2단계 비준 → 승급**.

### 정합성 스캔

CRITERIA 생성 직전에 한 번 수행하고, 새 응답으로 스테이징 몸체나 질문 목록이 달라질 때만
다시 수행한다.

| 축 | 확인할 사실 |
|---|---|
| 용어 | 같은 개념을 여러 말로 부르는가? |
| v1 경계 | 캐노니컬 후보와 LATER가 섞였는가? |
| 흐름 | 행위자·상황·의도·관측 가능한 결과가 있는가? |
| 예외 | 각 v1 코어 UseCase의 실패·취소·되돌림이 답/LATER/유보/해당 없음으로 처분됐는가? |
| 권한 | 여러 행위자가 같은 대상을 바꿀 때 권한·충돌 규칙이 처분됐는가? |
| 외부 약속 | 외부 사람·기관에 대한 위험한 약속의 업무 사실이 확인됐는가? |
| 파킹 | 모든 SF에 Essential `Trace:`가 있고 실행 수단 원문 이상으로 내용이 발전하지 않았는가? |
| 잔여 상태 | `[층미분류]`, 미처분 프라이어, 근거 없는 `[가정]`이 남았는가? |

걸림은 CRITERIA 필수 질문이나 QUESTIONS 유보로 라우팅한다. 한 번에 보여줄 걸림은 영향도 순
최대 3개로 제한하되, 걸림이 있어도 CRITERIA를 만들고 가장 값진 미답 하나로 회전한다.

### Harvest와 재기술

코퍼스에서 재발·공기·클러스터를 수확 리포트로 제안한다. 재발하거나 제거하면 흐름을 말할 수
없는 load-bearing 싱글턴만 Domain 후보로 고르고, 이름은 사용자 사용 이력에서, 새 조어가
필요하면 `[가정]`으로 제안한다. `essential-domain` 후보를 먼저 큐잉하고 각 raw 흐름을 그
언어로 한 번만 재기술해 `essential-usecase` 후보로 큐잉한다 — UseCase 후보는 받치는 Domain
후보에 `Blocked by:`로 묶인다. raw 코퍼스는 고쳐 쓰지 않고, 파킹은 harvest 대상에서
제외하며 확정된 Essential 용어로 Trace 표기만 정리한다.

### CRITERIA — Essential 인계 준비도

CRITERIA는 수요 문서다 — v1 몸체를 확정하기 전에 답이 있어야 할 질문·상태·답 포인터만 두고,
답 본문은 캐노니컬 후보에 둔다. 답의 출처는 캐노니컬(스테이징 중에는 비준 통과 후보)뿐이다.
비필수 유보는 QUESTIONS로 들려보내며 핸드오프를 막지 않는다.

```md
# SEED_BODY_CRITERIA

## 필수 질문

- [x] Q1. 핵심 행위자는 누구이고 어떤 가치를 얻는가? → ESSENTIAL_USECASE #1,#3
- [ ] Q2. {적립}과 {사용}은 v1에서 모두 다루는가? → 미답

## 비필수 유보

- Q7. 포인트 소멸 정책 → SEED_BODY_QUESTIONS.md
```

다음 네 축을 Essential 인계 준비도로 검사한다.

1. **예외 처분** — 각 v1 코어 UseCase의 실패·취소·되돌림이 답, LATER, 명시 유보 또는
   사용자 확인 `해당 없음` 중 하나를 가진다.
2. **판정 가능한 결과** — 각 Then이 사용자가 무엇을 관측하면 성공인지 말한다.
3. **권한·충돌** — 여러 행위자가 같은 대상을 다루는 경우 규칙을 갖는다. 그런 구조가 없으면
   몸체 전체에서 한 번 `해당 없음`을 확인한다.
4. **외부 약속** — 위험한 외부 사람·기관이 있으면 실제 업무 약속과 책임을 확인한다.
   채널·API·인증 같은 구현 계약은 요구하지 않는다. 없으면 한 번 `해당 없음`을 확인한다.

활성 프라이어도 전부 처분돼야 한다. 모든 필수 질문이 체크되고 확정 후보 포인터를 가질 때만
내용 비준으로 간다. 질문의 추가·삭제·필수/비필수 변경은 메타 비준을 다시 받되, 기존 질문에
답이 생긴 것만으로는 재비준하지 않는다.

미답 질문에 사용자가 "모르겠어", "네가 보기엔?"이라고 하면 구체 제안 하나를 `[가정]` 후보로
만들어 근거와 함께 묻는다. 승인이면 비준 턴이 Evidence가 되고, 기각이면 REJECTED에 기록해
같은 제안을 반복하지 않는다. 제안 본문을 CRITERIA에 넣지 않는다.

### 2단계 배치 비준

| 단계 | 사용자 결정 | NO일 때 |
|---|---|---|
| **A. 메타** | "v1을 정의하는 질문이 이것들이 맞아?" | CRITERIA를 고치고 다시 A |
| **B. 내용** | "이 Essential 몸체 전체를 확정할까?" | 수정 반영 후 다시 B |

B에는 Domain 용어, UseCase 전문, LATER/QUESTIONS 요약, 걸림 처분을 모두 포함한다. 본문이
길면 스테이징 파일에 전문을 쓰고 대화에는 요약과 위치를 제시한다. 사용자는 전체 몸체를 한
번의 결정으로 비준·부분 수정·부분 기각한다. 아직 승인 기회가 없던 v1 밖 후보는 `LATER
신규`로 표시하고 B 통과가 명시 승인을 겸한다. 부분 기각은 REJECTED에 기록하고 관련 CRITERIA
상태를 되돌린다. 사용자가 "퀵", "그냥 묶어줘"라고 하면 A와 B를 한 질문으로 압축하되 스캔과
충족 판정은 그대로 수행한다.

## 승급과 인계

승급 전에 [references/artifacts.md](references/artifacts.md)를 읽고 그대로 materialize한다.
B 통과 후 순서:

1. Domain 후보를 먼저, 이어서 UseCase 후보를 캐노니컬 2문서로 materialize한다.
2. 모든 UseCase `[Term]`이 DOMAIN에 있고 `{term}`·작업 라벨이 새지 않았는지 검사한다.
3. 기존 대상 파일과 충돌하면 artifacts.md의 충돌 규칙대로 사용자 결정을 받는다.
4. 고정 인계 문서를 artifacts.md의 포맷대로 `docs/`에 두고, 명시 기각이 있으면 기각 기록도
   옮긴다.
5. 후보 큐 잔여는 질문으로 남길 가치가 있으면 QUESTIONS로 옮기고 아니면 폐기한다. 미비준
   후보를 LATER로 보내지 않는다.
6. 캐노니컬과 인계 문서를 다시 읽어 Evidence가 확정 근거를 모두 담는지 확인한 뒤 작업용
   코퍼스·프라이어·수확 리포트·후보 큐를 정리한다. 사용자가 run 백업을 원하면 정리 전에
   보존한다.

파킹된 SF는 확정된 System 설계가 아니라 후속 스킬이 다시 확인할 raw 시드다. 종료 시 다음
단계 카테고리(System 몸체 도출, 수요·시장 검증, PRD, 티켓, 프로토타입)만 제시하고 실행은
사용자의 다음 요청에 맡긴다. 재실행은 새 run과 새 비준으로 시작하되, 기존
`docs/SEED_BODY_REJECTED.md`가 있으면 기각 레지스트리로 읽어 같은 제안을 되풀이하지 않는다.

## 1. 뼈대 정합성 스캔

CRITERIA 생성 직전에 한 번 수행한다. 새 응답으로 스테이징 몸체나 질문 목록이 달라질 때만 다시
수행한다.

| 축 | 확인할 사실 |
|---|---|
| 용어 | 같은 개념을 여러 말로 부르는가? |
| v1 경계 | 캐노니컬 후보와 LATER가 섞였는가? |
| 흐름 | 행위자·상황·의도·관측 가능한 결과가 있는가? |
| 예외 | 각 v1 코어 UseCase의 실패·취소·되돌림이 답/LATER/유보/해당 없음으로 처분됐는가? |
| 권한 | 여러 행위자가 같은 대상을 바꿀 때 권한·충돌 규칙이 처분됐는가? |
| 외부 약속 | 외부 사람·기관에 대한 위험한 약속의 업무 사실이 확인됐는가? |
| 파킹 | 모든 SF에 Essential `Trace:`가 있고 실행 수단 원문 이상으로 내용이 발전하지 않았는가? |
| 잔여 상태 | `[층미분류]`, 미처분 PRIOR, 근거 없는 `[가정]`이 남았는가? |

걸림은 CRITERIA 필수 질문이나 QUESTIONS 유보로 라우팅한다. 한 번에 사용자에게 보여줄 걸림은
영향도 순 최대 3개로 제한한다. 걸림이 있어도 CRITERIA를 만들고 가장 값진 미답 하나로 회전한다.

## 2. Harvest와 재기술 큐잉

1. `SEED_BODY_ESSENTIAL_FLOWS.md`에서 재발·공기·클러스터를
   `SEED_BODY_HARVEST.md`에 제안한다.
2. 재발하거나 제거하면 흐름을 말할 수 없는 load-bearing 싱글턴만 Domain 후보로 고른다.
3. 이름은 사용자 사용 이력에서 고른다. 새 조어가 필요하면 `[가정]`으로 제안한다.
4. `essential-domain` 후보를 먼저 큐잉하고, 각 raw 흐름을 그 언어로 한 번만 재기술해
   `essential-usecase` 후보로 큐잉한다. UseCase 후보는 `Blocked by:`로 Domain 후보를 가리킨다.
5. raw 코퍼스는 고쳐 쓰지 않는다. `SYSTEM_PARKING`은 harvest 대상에서 제외하고, 확정된
   Essential 용어로 Trace 표기만 정리한다.

## 3. CRITERIA — Essential 인계 준비도

CRITERIA에는 v1 몸체를 확정하기 전에 답이 있어야 할 **질문과 상태와 답 포인터**만 둔다.
답 본문은 캐노니컬 후보에 둔다.

```md
# SEED_BODY_CRITERIA

## 필수 질문

- [x] Q1. 핵심 행위자는 누구이고 어떤 가치를 얻는가? → ESSENTIAL_USECASE #1,#3
- [ ] Q2. {적립}과 {사용}은 v1에서 모두 다루는가? → 미답

## 비필수 유보

- Q7. 포인트 소멸 정책 → SEED_BODY_QUESTIONS.md
```

다음 네 축을 Essential 인계 준비도로 검사한다.

1. **예외 처분** — 각 v1 코어 UseCase의 실패·취소·되돌림이 답, LATER, 명시 유보 또는 사용자
   확인 `해당 없음` 중 하나를 가진다.
2. **판정 가능한 결과** — 각 Then이 사용자가 무엇을 관측하면 성공인지 말한다. 시간·복구·품질이
   사용자 성공 조건이면 여기 남기고 구현 방법만 파킹한다.
3. **권한·충돌** — 여러 행위자가 같은 대상을 다루는 경우 규칙을 갖는다. 그런 구조가 없으면
   몸체 전체에서 한 번 `해당 없음`을 확인한다.
4. **외부 약속** — 위험한 외부 사람·기관이 있으면 실제 업무 약속과 책임을 확인한다. 채널·API·
   인증 같은 구현 계약은 요구하지 않는다. 외부 약속이 없으면 몸체 전체에서 한 번 `해당 없음`을
   확인한다.

활성 PRIOR도 전부 처분돼야 한다. 모든 필수 질문이 체크되고 확정 후보 포인터를 가질 때만 내용
비준으로 간다. 질문의 추가·삭제·필수/비필수 변경은 단계 A를 다시 비준받는다. 기존 질문에 답이
생긴 것만으로는 재비준하지 않는다.

## 4. 예시답안 보조

미답 질문에 사용자가 “모르겠어”, “네가 보기엔?”이라고 하면 구체 제안 하나를 `[가정]` 후보로
만들어 근거와 함께 묻는다. 승인이면 비준 턴을 Evidence로 삼고, 기각이면 `REJECTED`에 기록해
같은 제안을 반복하지 않는다. 제안 본문을 CRITERIA에 넣지 않는다.

## 5. 2단계 배치 비준

| 단계 | 사용자 결정 | NO일 때 |
|---|---|---|
| **A. 메타** | “v1을 정의하는 질문이 이것들이 맞아?” | CRITERIA를 고치고 다시 A |
| **B. 내용** | “이 Essential 몸체 전체를 확정할까?” | 수정된 후보와 질문 상태를 반영하고 다시 B |

B에는 Domain 용어, UseCase 전문, LATER/QUESTIONS 요약, 걸림 처분을 모두 포함한다. 본문이 길면
스테이징 파일에 전문을 쓰고 대화에는 요약과 파일 위치를 제시한다. 사용자는 여전히 전체 몸체를
한 번의 결정으로 비준·부분 수정·부분 기각한다.

B에 아직 승인 기회가 없던 v1 밖 후보가 있으면 `LATER 신규`로 표시한다. B 통과가 그 항목의
명시 승인도 겸한다. 부분 기각은 `SR-nnn`으로 기록하고 관련 CRITERIA 상태를 되돌린다.

사용자가 “퀵”, “그냥 묶어줘”처럼 명시하면 A와 B를 한 질문으로 압축할 수 있다. 스캔과 CRITERIA
충족 판정은 그대로 수행한다.

## 6. 캐노니컬 승급

B 통과 후 다음 순서를 지킨다.

1. Domain 후보를 먼저, 이어서 UseCase 후보를 캐노니컬 2문서로 materialize한다.
2. 모든 UseCase `[Term]`이 DOMAIN에 있고 `{term}`·후보 라벨이 새지 않았는지 검사한다.
3. 기존 대상 파일과 충돌하면 [artifacts](artifacts.md)의 충돌 규칙대로 사용자 결정을 받는다.
4. [artifacts](artifacts.md)의 승급 경로에 적힌 고정 인계 문서를 그 포맷 규칙대로 `docs/`에 둔다.
5. artifacts의 선택 감사 조건을 만족하면 기각 기록도 이동한다.
6. CANDIDATES 잔여는 사용자에게 질문으로 남길 가치가 있으면 QUESTIONS에 옮기고, 아니면 폐기한다.
   미비준 후보를 LATER로 보내지 않는다.
7. 캐노니컬 Evidence가 raw 흐름의 확정 근거를 모두 담는지 확인한 뒤 작업용 FLOWS·PRIOR·
   HARVEST·CANDIDATES를 정리한다. 사용자가 run 백업을 원하면 정리 전에 보존한다.

## 7. 종료 패키지와 다음 단계

종료 패키지의 정확한 핵심·고정 인계·선택 감사 구성은 [artifacts](artifacts.md)를 단일
진실원천으로 따른다.

`SYSTEM_PARKING`의 SF는 확정된 System 설계가 아니라, 후속 스킬이 다시 확인할 raw 시드다.
다음 단계에서는 이 패키지를 입력으로 System 몸체 도출, 수요·시장 검증, PRD, 티켓, 프로토타입
중 가능한 카테고리만 제시한다.

재실행은 새 `.scratch/seed-body/` run과 새 비준으로 시작한다. 기존
`docs/SEED_BODY_REJECTED.md`가 있으면 초기 기각 레지스트리로 읽어 같은 제안을 되풀이하지 않는다.

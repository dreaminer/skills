# Grow Loop

기획은 넓게, 깊이는 지금 만드는 조각에만 둔다. 사람의 판단은 문서보다 **돌아가는 결과**를
보고 내릴 때 싸고 정확하다. 그래서 한 사이클마다 사람이 결정하는 지점은 둘뿐이다 — 조각
승인과 결과 리뷰.

```text
방향(1회) → [조각 정하기 → 구현 → 리뷰] → 조각 정하기 → …
```

상태는 대상 프로젝트의 `docs/GROW.md` 한 파일에 둔다. 파일이 있으면 그 상태에서 이어가고,
없으면 방향부터 시작한다.

## 대화 규칙

모든 단계에 적용한다.

- 한 턴에 질문 하나. 사용자가 자기 말로 답하게 묻는다.
- **발화 근거**: 방향·용어·AC의 주장은 사용자 턴의 짧은 직접 인용에 묶는다. 에이전트의
  유추는 `[가정]`으로 적고, 사용자가 확인한 턴부터 근거가 된다.
- **의도와 수단 구분**: 의도·정책·관측 가능한 결과는 기획이다. 사용자가 결과를 이루는
  방법으로 말한 기술 수단("푸시로", "Redis에")은 원문 그대로 `구현 메모`에 두고, 그 수단이
  필요한 조각의 기술 선택 때 다시 확인한다.
- **제안**: 같은 질문에 두 번째로 오거나 사용자가 모른다고 하거나 먼저 물으면, 지금까지
  확정된 내용에서 도출한 구체안 하나를 `[가정]`으로 낸다. 여러 안을 늘어놓지 않는다.

## 1. 방향

목표는 핵심 행위자가 흐름에 진입하는 지점부터 핵심 가치를 얻는 지점까지의 **사슬**을 사용자
말로 잇는 것이다. 사슬의 빈 구간(앞뒤로 무엇이 이어지는가)을 먼저 묻는다. 한 단계의
규칙·수치·예외는 그 단계를 만드는 조각에서 묻는다 — 사용자가 한 지점을 깊게 말하면 받아
적고 사슬로 돌아온다.

용어는 미리 열거하지 않는다. 같은 개념이 대화에서 반복되거나 빼면 흐름을 말할 수 없을 때
`용어`에 올리고, 이름은 사용자가 쓰는 말로 정한다. 같은 개념을 두 말로 부르면 하나로
수렴하자고 묻는다.

**완료**: 실제 용어로 "누가 어떤 흐름을 통해 어떤 가치를 얻는가"를 빈칸 없이 한 문단으로
쓸 수 있고, 그 사슬을 덮는 조각 후보가 제목 수준으로 있고, 사용자가 이 방향을 한 번
확인했다. 예외 목록과 기능 전체 목록은 완료 조건이 아니다.

## 2. 조각 정하기

**조각**은 실제 진입점(약속한 UI가 있으면 그 화면)에서 들어가 실제 배선을 지나 사용자가
관측할 수 있는 결과까지 관통하는 가장 얇은 세로 경로다. 첫 조각은 사슬의 핵심 가치가
처음 성립하는 경로를 고른다.

현재 조각에 다음을 정한다.

- **확인할 결과**: 사용자가 실행해서 직접 볼 것.
- **이번엔 안 다룸**: 경계를 명시한다. 상세화 중에 새 기능이나 예외가 나오면 다음 조각
  후보 제목으로 적고, 사용자가 지금 필요하다고 결정한 것만 현재 조각에 넣는다.
- **AC**: 이 조각의 행동 수용 조건. `Given/When/Then`과, `Then`을 관측할 가장 낮은 안정된
  공개 경계인 **seam**. `Then`은 무엇을 관측하면 성공인지 말한다.
- **전역 규칙**: 이 조각이 건드리는 도메인 불변식(권한, 허용 집합, 상태 규칙 등). 규칙마다
  반례로 따진다 — 이 조각의 AC를 모두 만족하면서 그 규칙을 어기는 구현이나 진입 경로가
  있는가? 있으면 그 반례에서 실패할 assertion을 기존 AC에 보강하고, 부족할 때만 AC를
  추가한다. 규칙이 금지(허용 집합 밖, 권한 없는 행위)라면 그 금지된 요청을 실제로 보내 거부를
  관측하고, 규칙이 성립 조건(수락된 주문엔 수락 시각이 있다)이라면 정상 경로의 결과로 관측한다.
- **기술 선택**: 이 조각을 실제로 돌리는 데 필요한 것만 (저장소, 외부 연동, 런타임 등).

질문은 이번 조각을 실행하는 데 필요한 결정으로 한정한다. 다른 조각의 정책 질문은 그 조각
제목 아래 메모로 남기고 넘어간다.

**완료**: 위 항목을 한 번에 보여 주고 사용자가 "이 조각으로 간다"를 승인했다. 바꿀 항목만
짚게 하고, 고친 항목만 다시 보여 준다.

## 3. 구현

AC 하나씩 tracer bullet으로 진행한다.

1. seam에서 AC를 실행하는 테스트를 쓰고 **RED**를 관측한다 — `Then`의 assertion이 실패하거나
   seam 자체가 없어서 실패해야 한다. 하네스·설정 오류는 RED가 아니라 고칠 대상이다.
2. AC를 만족하는 최소 구현으로 **GREEN**. 대상 테스트와 기존 테스트가 모두 통과한다.
3. `GROW.md`의 해당 AC에 테스트 위치, 실행 명령, 이번에 관측한 결과를 기록한다.

**바로 통과할 때**: 앞 조각이 이미 그 행동을 만들었을 수 있다. 테스트가 seam에 닿고 모든
`Then`을 단언하는지 확인하고, 임시 사본에서 그 행동을 깨뜨렸을 때 의도한 assertion에서
실패하는지 본다. 실패하면 원본에서 다시 GREEN을 확인하고 Result에 `이미 충족: <깨뜨린 방법과
실패한 assertion>`을 남긴다. 실패하지 않으면 테스트를 보강한다. AC나 기대값은 그대로 둔다.

AC가 모호하거나 방향·용어·다른 AC와 충돌하면 구현을 멈추고 사용자에게 그 결정 하나를 묻는다.
답은 [기획 변경](#기획-변경) 절차로 반영하고 이어간다.

**실제 배선**: mock으로 얻은 GREEN은 행동 격리의 증거일 뿐이다. 기술 선택은 실제
드라이버·어댑터·런타임으로 동작을 확인하고, 확인할 결과는 실제 진입점에서 관측한다.

**리팩터**: 조각의 AC가 모두 GREEN이면, 이번 조각에서 드러난 중복, 용어와 어긋난 이름, 도메인
경계를 가로지르는 코드만 정리한다. 이름·경계는 현재 합의를 따르며, 합의가 바뀌면 기획과
코드·테스트를 함께 고친다. 정리 후 전체 테스트가 다시 GREEN이어야 한다.

**완료**: 현재 조각의 모든 AC가 이번 실행에서 GREEN으로 기록됐고, 전체 테스트가 통과하고,
사용자가 확인할 결과를 직접 볼 수 있게 앱이 실행 가능한 상태다.

## 4. 리뷰

한 번의 대화로 결과 리뷰와 다음 조각 선택을 묶는다.

보여 줄 것: 실행 방법과 확인할 결과를 보는 경로, AC 결과 요약, 이번엔 안 다룬 것.
물을 것: **관측한 결과 → 바꿀 점 → 다음 조각**. 바뀌는 것만 결정하고, 그대로인 방향·용어·AC는
다시 비준하지 않는다.

바꿀 점은 [기획 변경](#기획-변경) 절차로 반영한다.

**완료**: 다음 조각이 정해졌으면 2로 간다. 사용자가 목표 도달이나 중단을 말하면 루프를 끝내고,
남은 조각 후보와 `stale` AC를 보고한다.

## 기획 변경

방향·용어·AC·전역 규칙·조각 목록이 바뀌면, 어느 단계에서 바뀌었든 이 순서를 따른다.

1. 기획을 먼저 고친다.
2. 바뀐 AC와, 바뀐 용어·전역 규칙을 쓰는 AC의 결과를 끝난 조각까지 포함해 `stale`로 바꾼다.
3. `결정 기록`에 무엇을 왜 바꿨는지 한 줄로 남긴다.

`stale` AC는 증거가 아니다. 다음 구현 단계에서 현재 조각의 AC보다 먼저, 테스트의 seam과
assertion이 바뀐 계약에 맞는지 확인하고 고친 뒤 다시 실행해 GREEN을 관측한다.

## `docs/GROW.md`

```md
# GROW

## 방향
<누가 어떤 흐름을 통해 어떤 가치를 얻는가 — 한 문단> (T3 "…")

## 용어
- **주문**: 회원이 매장에 요청한 상품 묶음 (T5 "…")

## 구현 메모
- "푸시로 알림" (T7) — S3 기술 선택 때 확인

## 조각
- [x] S1 회원이 첫 주문을 넣는다
- [ ] S2 매장이 주문을 수락한다 ← 현재
- [ ] S3 주문 취소 — 메모: 수락 후 취소 가능 여부

## S2 매장이 주문을 수락한다
확인할 결과: …
이번엔 안 다룸: …
전역 규칙: …
기술 선택: …

### AC-S2-1 <제목>
Given … / When … / Then …
Seam: …
Test: <프로젝트 상대 경로> · `<실행 명령>`
Result: green 2026-11-10 exit 0 | red | stale | 없음

## 결정 기록
- 2026-11-10 S1 리뷰: 주문 확인 화면에 매장 이름 추가 → AC-S1-2 수정, stale
```

끝난 조각의 섹션과 AC는 지우지 않는다. 회귀를 막는 계약으로 남는다.

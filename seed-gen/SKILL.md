# Seed Gen — 기존 프로젝트에서 Essential 몸체 유추하기

seed로 관리되지 않는 기존 프로젝트를 seed 흐름에 태우는 입구다. 기존 도메인 문서는 있어도 되고
없어도 된다. 사용자의 굵은 설명, 코드, 기존 도메인 문서를 재료로 **도메인 언어를 유추한 초안**을
만들고, 사람이 다듬어 비준한 결과를 seed-body와 **같은 인계 패키지**로 남긴다. 승급 이후 도메인의
원천은 이 패키지 하나다. 이 스킬이 만드는 것은 문서뿐이다 — 코드와 테스트는 읽기만 하고, 비준은 사람의
답으로만 이뤄진다. 문서와 구현을 해시·테스트로 묶는 일은 이어지는 `$seed-loop`
(seed-system → seed-tdd)의 몫이다.

운영 전과 규칙 변경 전에 `DESIGN.md`의 불변식을 읽는다 — 기존 seed 스킬을 바꾸지 않는다는 조건과,
그 조건에 부딪혔을 때의 처리가 거기 있다.

## 정체성 원칙

이 목록은 동결이다. 판단 지침이며, 원칙 추가 — 의미상 의무를 늘리는 재표현 포함 — 는 사용자
비준을 요구한다. 여기 없는 대화·수렴 규범은 sibling seed-body를 따른다.

1. **유추는 가정이다** — 생성한 도메인 용어·흐름·UseCase는 전부 `[가정]`이고, 사용자가 비준한
   턴부터 근거가 된다. 용어는 사용자의 굵은 설명에 비추어 "이 코드가 어떤 업무를 하는가"를
   유추해 업무 언어로 짓는다. 코드 식별자는 유추의 단서다 — `OrdHdr`, `OrdSvc.submit()`이
   보이면 "주문", "주문 확정"처럼 업무 언어로 옮긴다. 기존 도메인 문서도 같은 재료다 — 문서에 적힌
   용어·규칙도 `[가정]`으로 올리고, 이번 세션의 비준 턴부터 근거가 된다. 이름은 비준 과정에서
   사용자 언어로 수렴한다.
2. **관측된 동작을 의도로 채택할지는 사람이 교정해 정한다** — 에이전트는 도달 여부·분기·연결을
   조사하고, 버그·우연·죽은 코드로 보이는 곳마다 처분안(2단계 판정 처분 표의 한 행)을 `[가정]`으로
   붙여 초안에 넣는다. 사람이 교정하거나 승인한 턴부터 확정이다. 기존 테스트가 GREEN인 것도
   의도의 증거가 아니다.
3. **v1은 현재 구현 중 비준한 것** — 지금 코드가 제공하는 것 중 사람이 Essential로 비준한 집합이
   v1(캐노니컬)이다. 기존 기능이 원래 의도한 올바른 규칙은 기능이 이미 있으므로 v1에 든다.
   구현에 없는 것은 사용자가 승인하면 LATER로 간다.

## sibling 스킬

이 스킬 옆에 설치된 `seed-body`와 `seed-system`을 resolve한다. 없으면 설치 위치를 한 번 묻고,
확인할 수 없으면 멈춘다. 다음은 seed-body가 단독 소유하며 여기서 재기술하지 않는다.

- 인계 패키지 경로·파일 스키마·Evidence·정의 링크·충돌 규칙: `seed-body/references/artifacts.md`
- 사용자 교정의 처리 — 턴 처리 1–5(근거 고정, Essential admission, 되비춤과 기록, v1 경계, 승격 체크),
  작업 라벨(`[가정]`·`[충돌]`·`[층미분류]`): `seed-body/SKILL.md`「발산 — 턴 처리」
- 수렴과 승급: `seed-body/SKILL.md`「수렴 — 종료 게이트」「승급과 인계」
- 작업 보기: `seed-body/SKILL.md`「작업 보기 — Archify」

seed-body의 「카테고리 프라이어」, 「질문 처분」, 「종료 임박 휴리스틱」, 「첫 턴」 초대는 대화로
빈칸을 채워 가는 경로라 쓰지 않는다. seed-gen은 **생성 → 교정**이다 — 1단계가 모든 슬롯을 `[가정]`으로
채우고, 사용자는 고칠 것만 말하며, 수렴 진입은 사용자의 승인("됐다")이다.

## 0. 진입

대상 프로젝트와 슬라이스(관측 가능한 가치 흐름 하나)를 확정하고 인계 docs 경로를 정한다.
프로젝트 전체가 한 슬라이스면 루트의 `docs/`, 여러 슬라이스로 나누면 각 슬라이스 디렉터리의
`docs/`다 — 하류 seed 스킬이 이 위치를 기준으로 읽는다. 위에서부터 첫 일치로 분기한다.

1. 이 슬라이스의 `.scratch/seed-gen/` 작업 상태가 있으면 거기서 재개한다.
2. 그 docs에 비준된 유효 인계 패키지 — artifacts.md가 정한 ESSENTIAL 2문서와 SEED_BODY 고정
   인계 4문서 — 가 있으면 멈추고 `$seed-loop`(또는 `$seed-system`)를 안내한다.
3. 그 밖이면 새로 시작한다. 기존 도메인 문서 — 도메인 용어·유스케이스·업무 규칙을 서술한
   문서(README의 해당 절, 기획·결정 기록, 다른 도구가 만든 도메인 문서 등) — 의 목록을 작업 메모에
   남긴다. 패키지 파일과 이름·경로가 같은 문서는 이 목록이 아니라 artifacts.md의 충돌 규칙
   (덮어쓰기/병합/보류)으로 승급 시점에 처리한다.

## 1. 생성

에이전트 단독으로 초안을 만든다. 먼저 사용자의 **굵은 설명**을 받는다 — 무슨 서비스이고, 누가,
무엇을 하려고 쓰는가. 설명이 유추의 기준이므로 생성은 설명을 받은 뒤에 시작한다. 설명의 사용자
턴은 이후 Evidence의 첫 근거가 된다.

1. 슬라이스의 트리거(라우트, CLI, 잡, 컨슈머, UI 액션)를 찾아 각 트리거에서 관측 가능한 결과까지
   흐름을 따라간다.
2. 각 흐름을 정체성 원칙 1로 업무 언어 문장으로 옮겨 Essential 흐름 초안을 쌓는다. 실행 수단
   (재시도, 캐시, 큐 등)은 seed-body 정체성 원칙 2로 걸러 작업 메모에만 둔다. 기존 도메인 문서가
   있으면 함께 읽고, 문서와 코드가 어긋나는 곳은 의심 지점으로 남긴다.
3. 흐름 초안에서 Domain·UseCase 초안을 만든다. 이것은 제시용 첫 수확이고, 비준 대상 후보는
   2단계 수렴의 harvest가 사용자 답을 반영해 다시 확정한다. 흐름:UseCase는 N:M이다.
4. 작업 메모(`.scratch/seed-gen/`, 자유 형식)에 남긴다: 코드 식별자 ↔ 도메인 용어 대응, 흐름별
   코드 위치, 정적 읽기로 도달하지 못한 영역(동적 디스패치, DB 트리거, 외부 라우팅 등), 의심 지점.

완료 기준: 슬라이스의 트리거에서 흐름 초안과 Domain·UseCase 초안이 나왔고, 도달하지 못한 영역
목록이 작업 메모에 있다.

## 2. 비준

1. **초안 제시** — 작업 보기(Archify)와 함께 초안 전체를 문서 형태로 한 번 보여 준다. 초안은 Domain·
   UseCase만이 아니라 서비스의 목적, v1 범위, 의심 지점마다의 처분안까지 에이전트가 `[가정]`으로
   채운 상태다. 지도에는 유추의 출처(코드 위치·기존 문서 → 도메인 용어)와 의심 지점을 함께 그리고,
   "읽지 못한 영역"을 한 줄 덧붙인다. 끝에 "고칠 것만 말해줘"라고 한 줄로 청한다. Archify가 없거나
   실패하면 같은 원천의 텍스트 보기로 잇는다.
2. **교정 반영** — 사용자의 교정을 seed-body 턴 처리 1–5로 반영하되, 4번 v1 경계는 정체성 원칙 3을
   기준으로 판정한다. 반영한 초안을 바뀐 곳이 보이게 다시 보여 주고, 사용자가 승인할 때까지 반복한다.
   에이전트가 먼저 묻는 것은 교정이 모호하거나 두 갈래로 읽힐 때 그 한 가지뿐이다. 턴 처리 4–5의
   확인(v1 경계, 승격 체크)과 수렴의 정합성 스캔 걸림도 처리 논리만 쓰고, 별도 질문 대신 `[가정]`으로
   초안에 반영해 재제시·일괄 승인으로 처리한다.
3. **판정 처분** — 사람이 확정한 버그·낡음·불요 판정은 다음으로 보낸다.

   | 사람의 판정 | 기각된 쪽 | 캐노니컬 |
   |---|---|---|
   | 코드가 버그, 올바른 동작을 지금 말함 | 코드 동작 → REJECTED (사유: 코드 관측 + 버그 판정) | 올바른 규칙 |
   | 코드가 버그, 올바른 동작은 모름 | QUESTIONS 유보 | — |
   | 문서가 낡음, 코드가 의도 | 문서 주장 → REJECTED (사유: 기존 문서 + 낡음 판정) | 코드 동작 |
   | 불요(죽은 기능 등) | REJECTED (사유: 불요) | — |
   | 의도된 동작(의심 해소) | — | 코드 동작 (현행 유지) |

   REJECTED 기록은 재실행·개정 때 같은 후보를 다시 올리지 않기 위한 것이고 하류로 전달되지 않는다.
   하류로 가는 것은 캐노니컬에 들어간 올바른 규칙이며, 그 검증과 구현 수정은 seed-system·seed-tdd가
   맡는다. 올바른 동작을 모르는 항목은 캐노니컬에서 빠지므로 하류의 보호도 수정도 받지 않는다 —
   그 항목이 v1 필수 질문이면 CRITERIA대로 답이 나올 때까지 승급하지 않는다.
4. **수렴** — 사용자가 승인하면 seed-body「수렴 — 종료 게이트」의 고정 순서(정합성 스캔 → harvest와
   재기술 → CRITERIA → 배치 비준)를 수행한다. 스캔 걸림과 CRITERIA 필수 질문도 에이전트가 `[가정]`
   답을 채운 초안으로 제시하고, 메타 비준과 내용 비준을 한 번에 받는다(seed-body「2단계 배치 비준」의
   압축 경로). 사용자가 나눠 보길 원하면 두 단계로 받는다. `해당 없음`도 배치에 명시해 승인받고,
   CRITERIA는 seed-body 규약대로 답 본문이 아니라 캐노니컬 후보 포인터를 둔다.

## 3. 승급과 종료

seed-body「승급과 인계」와 artifacts.md대로 그 슬라이스의 docs에 materialize한다.

- 캐노니컬 Evidence는 artifacts.md 형식(턴 + 짧은 인용) 그대로다. 사용자의 굵은 설명과 비준
  턴이 근거이고, 코드 위치는 작업 메모에 둔다.
- SYSTEM_PARKING의 SF는 사람이 세션에서 실행 수단으로 말한 조각만 둔다. 나머지 System 사실의
  원천은 코드 자체다.
- 승급 직후 `python3 <seed-system-skill>/scripts/check-acceptance.py --docs <그 docs> --links-only`로
  정의 링크를 확인한다. 이는 링크 확인이며 패키지 유효성 판정은 아니다.

materialize와 링크 확인이 끝난 뒤 **기존 도메인 문서를 처분**한다 — 승급 이후 원천이 둘이 되지
않게 하려는 것이다. 0단계 목록을 보여 주고 문서마다 사용자의 선택(보관 폴더로 이동, "seed 패키지로
대체됨" 표기 후 유지, 삭제)을 받아 그대로 실행한다. 그 docs에 있는 `SYSTEM_DOMAIN.md`·
`SYSTEM_USECASE.md`는 이동·삭제 중에서 고른다 — 남아 있으면 이후 seed-system checker가
ACCEPTANCE와의 mixed-mode로 실패한다. 저장소 밖 문서처럼 직접 실행할 수 없는 처분은 사용자에게
맡기고 목록에 그렇게 적는다.

종료 시 다음을 알린다.

```text
Essential 몸체를 비준해 <그 docs>에 남겼어. 아직 문서만 있고 구현과는 묶이지 않았어.
기존 도메인 문서 처분: <문서별 처분과 보관 위치>
다음은 $seed-loop로 AC를 만들고 테스트로 기존 구현과 묶는 단계야.
```

## 첫 턴

호출문에 서비스 설명이 없으면 대상 경로를 확인한 뒤 한 줄로 묻는다.

> 이 프로젝트가 어떤 서비스인지 굵게 설명해줘 — 누가, 무엇을 하려고 쓰는지. 코드와 docs는 내가
> 읽을게. 도메인을 설명한 문서가 다른 곳에 있으면 위치도 알려줘.

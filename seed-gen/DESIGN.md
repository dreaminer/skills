# Seed Gen — 설계 결정

운영 절차는 여기 없다. `SKILL.md`를 바꾸기 전에 이 문서의 불변식·소유 지도·편집 게이트를 먼저
적용한다.

## 불변식 — 기존 seed 스킬 무수정 (2026-10-25, 사용자 결정)

> 사용자 요구: 기존 seed 스킬의 흐름은 이 추가로 영향받지 않아야 한다.

- seed-body·seed-system·seed-tdd·seed-realize·seed-loop의 파일과 checker를 바꾸지 않는다.
- seed-gen은 seed-body의 인계 패키지 규약과 수렴 절차를 참조만 하고 재정의하지 않는다.
- 이 불변식을 깨야만 풀리는 문제가 생기면 seed-gen 쪽을 바꾸거나 사용자에게 올린다.
- 확인 기준은 HEAD가 아니라 seed-gen 작업 직전의 작업 트리다(기존 미커밋 변경은 별개).

설계·작성·범위 확대 독립 검토(2026-10-25, 마지막은 기존 도메인 문서 처분 반영본)는 원문
대조로 이 불변식이 성립한다고 판정했다. 근거:

- seed-loop의 차단 조건은 "구현 있음 + Seed 산출물 없음"이다(`seed-loop/SKILL.md:18-20`). 패키지가
  생기면 기존 규칙으로 seed-system에 진입한다.
- artifacts.md의 "코드가 없으므로"는 이유 서술이고 규약은 턴 + 인용이다. seed-gen은 규약을 따른다.
- 기존 동작은 seed-tdd `UNEXPECTED_GREEN → PREEXISTING_GREEN`, 어긋난 구현은 RED → Minimum GREEN
  경로가 이미 있다(`seed-tdd/references/test-quality.md:114-126`, `seed-tdd/SKILL.md` 4절).
- checker는 ESSENTIAL Evidence를 구조 필드로 파싱하지 않는다(`check-acceptance.py` REFERENCE_FIELDS).

실행으로 확인된 것은 아직 없다. "비준 이후 seed-body 산출물과 구분되지 않는다"는 **인계 패키지
형식과 seed-system 입력 계약까지**의 사실이다. 하류 문서에는 greenfield 전제 문구가 남아 있고
(`seed-system/DESIGN.md:9`, `seed-system/references/artifacts.md:71-72`, `seed-loop/SKILL.md:3`),
checker는 테스트를 실행하지 않으므로 묶임 여부는 seed-tdd의 실제 테스트 실행 결과로 확인한다.
하류 동작은 검증 상태의 관찰 항목이다.

## 결정 (2026-10-25)

**입구 하나만 만든다.** seed-loop가 권하는 "evidence-recovery flow"의 빈자리를 채운다. 비준
이후는 seed-body 산출물과 구분되지 않으므로, 차이는 비준 전 구간 — 무엇을 재료로 얼마나 먼저
제안하는가 — 에만 둔다. seed-body에도 `[가정]`·프라이어로 LLM 문장이 들어오는 경로가 있으므로,
실제 차이는 제안의 **양과 시점**(전체 초안 선제시)과 **재료**(굵은 설명 + 코드 + 기존 도메인 문서)다.

**대상은 seed로 관리되지 않는 기존 프로젝트다 — 도메인 문서 유무와 무관 (사용자 결정).** 처음에는
"코드만 있는 프로젝트"로 잡았으나, 사용자가 기존 도메인 문서가 있는 프로젝트도 seed 스킬로
관리하겠다고 범위를 정했다. 기존 도메인 문서는 굵은 설명·코드와 같은 **재료**이고 근거가 아니다 —
seed 규약의 Evidence는 이번 대화의 사용자 턴과 인용이며 문서는 턴이 아니다(다른 도구나 LLM이 쓴
문서는 사용자 발화도 아니다). 그래서 문서 내용도 `[가정]`으로 올려 다시 비준한다. 문서와 코드의
어긋남은 버그 판정과 같은 처분 표로 다룬다(문서가 낡았나, 코드가 버그인가).

**승급 이후 도메인의 원천은 seed 패키지 하나다 (사용자 결정).** 기존 도메인 문서를 그대로 두면 원천이
둘이 되어 어긋나기 시작한다. 승급(materialize·링크 확인) 직후에 기존 문서를 문서마다 사용자 선택(보관 이동 / 대체됨 표기 후
유지 / 삭제)으로 처분하고, seed-gen은 선택을 그대로 실행만 한다. 처분은 materialize와 링크 확인
**뒤에** 한다 — 순서가 반대면 승급이 보류·실패했을 때 기존 문서만 사라진다(독립 검토). 패키지와
이름·경로가 같은 문서는 처분 목록이 아니라 artifacts.md 충돌 규칙으로 처리한다 — 같은 경로에서
"유지"는 성립하지 않는다(독립 검토). `SYSTEM_DOMAIN.md`·`SYSTEM_USECASE.md`가
패키지 docs에 남으면 seed-system checker가 ACCEPTANCE와의 mixed-mode로 실패하므로
(`seed-system/scripts/check-acceptance.py`의 mixed-mode 검사) 그 둘은 유지 선택지에서 뺀다 — checker를
고치지 않는다는 불변식 때문이다.

**도메인 언어는 유추한다 (사용자 결정).** 사용자의 굵은 설명을 기준으로 코드가 하는 업무를 유추해
업무 언어로 짓는다. 코드 식별자를 그대로 쓰면 캐노니컬 언어가 코드에서 출발해 비준 후에도
seed-body 산출물과 달라진다(독립 검토 지적). 이름을 사용 이력이 아니라 유추로 먼저 제안하는 것은
seed-body 원칙 3의 변형이며, 비준 중 사용자 언어로 수렴시킨다.

**v1 = 현재 구현 중 비준한 것 (사용자 결정).** seed-body의 v1("처음 구현할 최소 흐름")을 그대로
쓰면 이미 있는 기능이 v1 밖(LATER)으로 밀리거나 하류 보호에서 빠진다. 새 기능 설계는
비준 이후 기존 흐름(LATER → seed-body 개정)의 몫이다. 버그 판정 시 기존 기능의 올바른 규칙은
기능이 이미 있으므로 v1에 든다.

**버그는 올바른 규칙을 캐노니컬에 넣어 하류로 넘긴다 (사용자 결정).** 문서와 구현의 불일치는
기존 seed 흐름에서 실패하는 테스트로만 드러나고, 그 테스트를 통과시키는 것이 구현 수정이다. 따라서
seed-gen은 별도 수정 장치를 두지 않는다. 코드의 현재 동작은 REJECTED에 사유와 함께 남기되 이는
재제안 방지용이다(seed-system 입력 계약에 REJECTED는 없다).

**문서와 구현을 묶는 일은 seed-loop 몫이다.** AC·해시는 seed-system, marker·테스트 연결은
seed-tdd가 소유한다. seed-gen이 하면 같은 일을 두 스킬이 소유하게 된다.

**make-body와는 무관하다 (사용자 지시).** 기존 `make-body`도 기존 코드의 Essential을 복원하지만
test-flows 선행을 요구하고 seed 인계 패키지를 만들지 않는다. 두 스킬을 연결하거나 합치지 않는다.

**seed-body의 카테고리 프라이어, 질문 처분, 종료 임박 휴리스틱, 첫 턴 초대는 쓰지 않는다.** 모두 대화로
빈칸을 채워 가는 경로다. seed-gen은 1단계 생성이 모든 슬롯을 채우고 사용자가 교정하므로, 사용자 교정의
처리(턴 처리 1–5, 작업 라벨)와 수렴·승급만 참조한다.

**생성 → 교정으로 비준한다 (사용자 결정, 2026-10-25).** 사용자의 원래 의도는 LLM이 알아서 초안을
생성하고 사람이 다듬거나 고치는 흐름이었다. 설계 검토에서 앵커링 우려를 반영하며 seed-body의 질문 회전(한 턴
한 질문, 첫 방문 무권고)을 끌어왔고, 첫 트레이스(기존 코드 프로젝트)에서 초안 제시 직후 에이전트가
서비스 목적을 질문으로 묻는 것으로 드러났고, 사용자가 생성 후 교정하는 방식이 아니라고
지적했다. 그래서 서비스 목적·v1 범위·의심 지점 처분안까지 에이전트가
`[가정]`으로 채운 초안을 내고, 사용자는 고칠 것만 말한다. 정체성 원칙 2를 "질문으로 올린다"에서 "처분안을
`[가정]`으로 붙이고 사람이 교정해 확정한다"로 바꿨다(사용자 비준). 손대지 않고 통과하는 `[가정]`이 그대로
확정되는 위험은 의도한 선택이며, 관찰 항목 1로 지켜본다. 비준의 근거가 이번 대화의 사용자 턴이라는
seed 규약은 그대로다 — 교정·승인 발화가 근거가 된다.

**초안은 Archify 작업 보기로 제시한다 (사용자 요청, 2026-10-25).** seed-body의 작업 보기는 사용자가
요청하거나 필요할 때 쓰는 보조지만, seed-gen은 생성한 초안 전체를 한 번에 판정받으므로 유추의
출처와 의심 지점이 보이는 지도가 기본이다. 보기는 파생물이며 근거·비준·완료 축이 아니다(seed-body
작업 보기 규약 그대로).

**명시 호출로만 실행한다 (사용자 결정, 2026-10-25).** `disable-model-invocation: true`. 사용자가
"명시적으로 호출하는 게 맞다"고 정했다. 그 결과 seed-loop의 차단 안내("evidence-recovery flow")에서
에이전트가 스스로 이 스킬로 넘어가지 않고, 사용자가 `/seed-gen`을 부른다. 전역 `body-shaping` 등
비슷한 상황의 스킬과 트리거가 경합하지 않는다.

## 소유 지도

한 사실은 한 곳만 산다.

| 사실 | 소유자 |
|---|---|
| 정체성 원칙 3개, 진입·생성·비준·승급 절차, 판정 처분 | `SKILL.md` |
| 불변식, 결정·근거, 편집 게이트, 검증 상태 | `DESIGN.md` |
| 인계 패키지·Evidence·정의 링크·충돌 규칙 | sibling `seed-body/references/artifacts.md` |
| 턴 처리 1–5, 작업 라벨, 수렴(정합성 스캔·Harvest·CRITERIA·배치 비준), 승급 | sibling `seed-body/SKILL.md` |

## 편집 게이트

seed-body `DESIGN.md`의 편집 게이트 3조를 그대로 적용한다 — 한 사실 한 소유자, 방어적 규칙은
실전 트레이스의 실행 실패가 있을 때만 승격, 스크립트가 없으므로 기계적 must 없음. 정체성 원칙
목록만 사용자 비준으로 바뀐다.

## 검증 상태

- 완료 트레이스 0회. 진행 중인 첫 트레이스(기존 코드 프로젝트)에서 사용자 보고 실행 실패 1건 —
  초안 제시 뒤 질문형 흐름 — 으로 2단계를 생성 → 교정으로 바꿨다. 완료 조건: 실제 기존 프로젝트 1 슬라이스로 seed-gen 승급 → `$seed-loop` →
  **seed-tdd AC 1건**(정상 동작 1건의 `PREEXISTING_GREEN`, 가능하면 버그 판정 1건의 RED → GREEN),
  그리고 기존 seed 스킬 diff 0 확인.
- 트레이스 확인처는 대상 프로젝트의 docs와 `.scratch/seed-gen/`, 세션 트랜스크립트다.

관찰 항목 (규칙 아님 — 관련 행동이 드러난 트레이스에서 삭제 / 유지 / 승격 중 하나로 처분):

1. 비준 중 사람이 바꾼 도메인 용어 비율, 손대지 않고 통과한 `[가정]` 비율 (앵커링 신호)
2. "읽지 못한 영역"이 비준 판단에 쓰였는가
3. seed-loop가 "Seed 출신이 아닌 구현 + Seed 산출물" 조합을 차단 없이 seed-system으로 보내는가
   (description의 "greenfield" 문구로 오판할 여지)
4. 버그 동작을 단언하는 레거시 테스트가 seed-tdd의 suite 통과 요건과 충돌해 BLOCKED가 되는가
5. 이미 정해진 stack·storage를 seed-system IP 단계와 seed-realize가 어떻게 다뤘는가
6. 복원된 몸체를 standalone으로 고칠 때 seed-body가 트리거되는가 (description이 "코드 없는 Seed")
7. 기존 도메인 문서가 있는 프로젝트에서: 문서 출신 `[가정]`의 재비준이 부담이었는가, 문서 처분 선택이
   실제로 어떻게 나왔는가, 다음 슬라이스에서 "대체됨" 문서·보관 폴더·다른 슬라이스 패키지가 다시
   재료로 들어왔는가
8. 구 체제 seed 문서가 일부만 남은 프로젝트(예: ACCEPTANCE는 있고 body 패키지가 불완전)에서
   새 ESSENTIAL과 기존 ACCEPTANCE 링크가 어떻게 되었는가 (checker의 stale link로 드러남)

설계 경위: 설계 초안 v3 → v4 → v5.1, 독립 검토 여러 회 (로컬 작업 노트, 저장소 밖).

# Rebuilder Stage

Stage 5는 Runner(Stage 1), Judger(Stage 3)와 같은 시스템 프로세스다. LLM 프롬프트가 아니며,
orchestrator가 결정론적 텍스트 치환으로 수행한다. 스킬 소스 전문을 LLM으로 재생성하지 않는다 —
이 단계에는 판단·해석·재서식이 개입할 자리가 없고, 실패는 그럴듯한 결과물 대신 명시적
`REBUILD_FAILED`로 드러나야 한다.

## 5-A. 입력

- 현재 버전의 스킬 원본 소스 (파일들)
- 4번에서 확정된 [최종 스킬 수정 제안서] — `proposer` 스킬이 정의한 exact-match edit 목록

## 5-B. 적용 절차

2단계로 수행한다. 검증 단계에서 edit 하나라도 실패하면 아무 파일도 수정하지 않는다
(all-or-nothing).

**1단계 — 전수 검증 (파일 무변경):**

각 edit을 종류별로 검사한다.

- 일반 edit ([기존 내용]이 원문 인용):
  - [Target 위치]의 파일이 존재하지 않으면 실패.
  - [기존 내용]과 글자 단위로 동일한 문자열이 그 파일에 정확히 1회 등장하지 않으면
    (0회 또는 2회 이상) 실패.
  - 다른 edit과 매칭 범위가 겹치면 실패.
- 신규 파일 edit ([기존 내용]이 `(신규 파일)`):
  - [Target 위치]의 경로에 파일이 이미 존재하면 실패. 기존 파일은 exact-match 치환으로만
    수정할 수 있으므로, `(신규 파일)`로 기존 파일을 통째로 갈아치우는 우회를 막는다.
  - 경로 부재는 이 종류의 edit에서만 실패 조건이 아니다.

**2단계 — 기계 적용 (나열 순서대로):**

- 일반 edit: 유일 매칭된 [기존 내용]을 [수정할 내용]으로 치환한다. Claude Code에서는 Edit
  툴이 이 계약(유일 매칭이 아니면 에러)을 그대로 강제하므로 edit당 Edit 호출 1회로 수행한다.
- 신규 파일 edit: [수정할 내용] 전체를 내용으로 하는 파일을 [Target 위치] 경로에 생성한다
  (Write 호출 1회).
- 제안서에 없는 변경은 어떤 이유로도 추가하지 않는다. 재서식, 오타 수정, 가독성 개선도
  금지다.

## 5-C. 출력

- 성공: 수정이 반영된 소스 파일들 자체가 산출물이다. 소스 전문을 별도로 출력하지 않는다.
  edit마다 apply log 한 줄을 남긴다 — `edit N: <파일 경로> 치환 완료` 또는
  `edit N: <파일 경로> 생성 완료`.
- 실패: `REBUILD_FAILED`와 실패한 edit 번호·사유(파일 부재 / 매칭 0회 / 매칭 N회 /
  파일 이미 존재 / 범위 겹침)를 기록하고 종료한다. 파일은 하나도 변경되어 있지 않아야 한다.
- `REBUILD_FAILED`로 끝난 루프의 이력 처리는 `proposer` 스킬의 Modification History Schema를
  따른다 (`outcome: FAILED (사유 표기)`).

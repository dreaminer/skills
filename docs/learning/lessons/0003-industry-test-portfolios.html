항상 두 벌로 돌리지는 않는다

대규모 조직도 테스트를 Acceptance 대 Characterization이라는 두 개의 고정 계층으로 운영하기보다, 변경 위험과 피드백 비용에 맞춘 포트폴리오로 운영한다.

Acceptance는 상시 제품 명세가 되기 쉽고, Characterization은 레거시 변경을 위한 상황별 기준선이 되기 쉽다.

일상적인 기능 개발새 요구의 acceptance와 기존 unit·integration·regression suite를 CI에서 실행한다.
테스트가 부족한 레거시 수정변경 영역에 characterization을 먼저 보강한 뒤 기존 suite와 함께 실행한다.
대규모 리플랫폼·마이그레이션동일 입력을 원본과 새 시스템에 재생하여 출력 동등성을 대량 비교한다.
안정화 이후가치 있는 기준선은 regression suite로 유지하고, 너무 넓거나 취약한 snapshot은 축소·제거한다.

공개된 두 사례

Google의 공개 테스트 지침은 대규모 suite를 테스트 이름 두 개로 나누기보다 속도, 유지비, 신뢰성 같은 속성으로 균형을 잡는다고 설명한다. AWS의 메인프레임 현대화 지침은 동일한 데이터셋을 원본과 대상 시스템에 재생하고 출력을 비교하는 기능 동등성 테스트를 제시한다. 후자는 characterization 방식이 특정 현대화 작업에서 크게 쓰이는 사례다.

Make Body에 주는 결론

모든 변경에 characterization을 의무화하지 않는다. 기존 suite가 충분하면 그것만 사용하고, 테스트가 없는 변경 경계나 동등성 보장이 중요한 리팩터링에만 기준선을 추가한다.

추가 질문은 에이전트에게 물어보라. 복습할 때는 빠른 판별표를 사용하면 된다.

Characterization Test란?

코드를 고치기 전에, 그 코드가 지금 실제로 하는 행동을 테스트로 사진 찍듯 고정하는 것이다.

“이 행동이 옳은가?”가 아니라 “이 행동이 지금 존재하는가?”를 검증한다.

예제

오래된 할인 함수가 있다. 요구사항은 없고 테스트도 없다.

discount(10000, "VIP")  // 실행해 보니 1700을 반환

왜 17%인지 아직 모른다. 그래도 변경 전에 현재 결과를 잠근다.

expect(discount(10000, "VIP")).toBe(1700)

이 테스트는 “VIP 할인은 17%가 맞다”는 정책을 승인하지 않는다. 리팩터링 후 결과가 달라졌다면 알려줄 뿐이다. 달라져야 하는 변경이라면 테스트 기대값도 의식적으로 바꾼다.

canonical System UseCase가 말하는 현재 실행 행동을 응답·저장 변화·이벤트 같은 관찰 가능한 경계에서 잠근다. System 문서는 설명이고, characterization test는 구현을 바꿨을 때 그 설명과 다른 행동이 생겼는지 실행해서 알려주는 안전장치다.

한 줄 확인

버그처럼 보이는 현재 동작도 characterization test에 담을 수 있을까? 그렇다. 담는 것은 승인하는 것이 아니라, 고칠 때 무엇이 달라지는지 명시적으로 만들기 때문이다.

더 궁금한 점은 에이전트에게 후속 질문하라. 빠른 복습은 참조 카드를 사용하면 된다.

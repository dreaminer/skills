둘은 무엇을 보고 있는가?

둘 다 입력과 결과를 검증하지만, 비교하는 기준이 서로 다르다.

Characterization은 현실을 보고, Acceptance는 약속을 본다.

하나의 변경으로 비교하기

현재 시스템은 결제된 주문에도 취소 요청을 허용한다. 새 요구사항은 “결제된 주문은 취소할 수 없다”이다.

Characterization test

Given 결제된 주문
When  취소 요청
Then  현재는 204를 반환하고 주문을 취소한다

이 테스트의 근거는 기존 코드를 실행해 관찰한 결과다. 이 결과가 옳다는 뜻은 아니다. 변경 전 현실을 명시해서, 무엇을 바꾸는지 보이게 한다.

Acceptance test

Given 결제된 주문
When  취소 요청
Then  취소를 거부하고 주문을 유지한다

이 테스트의 근거는 사람이 합의한 새 정책이다. 아직 구현하지 않았다면 처음에는 실패하는 것이 정상이다.

구현 후에는?

의도적으로 바꾸는 바로 그 행동에 대해서는 두 테스트가 모순된다. 낡은 characterization 기대값을 삭제하거나 새 정책으로 바꾸되, 취소 시 재고 복구처럼 변경 대상이 아닌 주변 행동의 characterization test는 계속 유지한다.

Acceptance test만 돌리면 안 되나?

기존 acceptance suite가 변경 주변의 보존할 행동까지 충분히 검증한다면 그래도 된다. Characterization test는 별도의 의무가 아니라, 테스트가 부족한 기존 코드에서 회귀 방지 범위를 채우는 임시·보완 수단이다.

새 요구사항 하나를 검증하는 acceptance test는 그 목표가 성공했는지만 보여준다. 같은 구현에서 알림 발송, 재고 처리, 권한 검사 같은 기존 행동이 우연히 깨져도 그 acceptance test가 관찰하지 않으면 통과한다. 이 빈 곳에만 characterization test를 추가한다.

그렇다면 왜 Acceptance를 더 쓰지 않나?

쓸 수 있고, 원하는 동작을 알고 있다면 그것이 더 낫다. 두 테스트는 실행 기술이나 커버리지 능력이 다르지 않다. Characterization의 실용적 이점은 정답을 합의하는 비용을 건너뛸 수 있다는 데 있다.

Acceptance의 기대값정책과 의도를 조사하고 사람과 합의해야 한다.
Characterization의 기대값기존 시스템을 실행하고 관찰한 값을 기록한다.

예컨대 레거시 API가 40개 필드의 응답을 만들고 있는데 내부 리팩터링만 해야 한다면, 40개 필드의 올바른 업무 의미를 모두 복원하는 것보다 대표 입력의 현재 응답을 golden master로 고정하는 편이 빠를 수 있다. 대신 우연한 형식과 기존 버그까지 잠글 수 있어 장기 명세로는 약하다.

따라서 Characterization은 더 넓거나 유연한 테스트가 아니라, 요구사항이 불완전할 때 더 싼 기준선이 될 수 있는 테스트다.

실패한 테스트먼저 물을 질문
Characterization이 기존 행동 변화가 의도된 범위인가?
Acceptance합의한 새 행동이 아직 구현되지 않았는가?

정답 확인

Characterization test다. 기대값의 출처가 요구사항이 아니라 현재 실행 결과이기 때문이다.

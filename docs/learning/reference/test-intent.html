두 테스트의 판별 기준

같은 테스트 코드라도 기대값을 어디서 가져왔느냐에 따라 역할이 달라진다.

CharacterizationAcceptance
비교 기준현재 구현에서 관찰한 행동사람이 합의한 원하는 행동
시간 방향과거·현재를 보존변경 후 목표를 제시
처음 작성할 때기존 코드에서 통과해야 함미구현 변경이라면 실패해야 함
실패의 기본 의미기존 행동이 달라짐요구사항을 아직 충족하지 못함
업무적 옳음보장하지 않음합의된 예제 범위에서 보장

판별 질문

  1. 기대값을 실행 결과에서 복사했는가? → Characterization
  2. 기대값을 요구사항·Essential 합의에서 가져왔는가? → Acceptance
  3. 둘 다 해당하는가? → 이미 올바르다고 합의된 기존 행동을 동시에 보존하는 테스트

Characterization이 필요 없는 경우

기존 acceptance·regression suite가 변경 영역에서 보존해야 할 행동을 이미 충분히 검증한다면 추가 characterization test는 필요 없다. 테스트되지 않은 현재 행동 중 이번 변경으로 깨질 위험이 있는 것만 보완한다.

Characterization의 경제성

더 유연한가?아니다. 현재 행동을 고정하므로 오히려 변경에 민감할 수 있다.
더 넓게 커버하는가?아니다. 입력과 assertion으로 정한 범위만 커버한다.
왜 쓰는가?올바른 기대값을 합의하지 않고도 현재 실행값으로 빠르게 회귀 기준선을 만들 수 있기 때문이다.
언제 Acceptance가 낫나?원하는 행동과 기대값을 이미 알고 있거나 확인할 수 있을 때다.

조직에서의 운영

일반 제품 개발에서는 acceptance·unit·integration·regression 테스트가 상시 CI suite를 이룬다. Characterization은 별도 영구 계층이라기보다 테스트가 부족한 레거시 코드의 변경, 리플랫폼, 동등성 검증 때 필요한 범위에 추가되는 역할이다.

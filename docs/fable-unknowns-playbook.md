# Fable Unknowns Playbook

이 문서는 Tech Bridge의 `[한영자막] Anthropic Thariq Shihipar의 Fable 활용 가이드`
영상을 바탕으로, 점점 강해지는 모델을 다루기 위한 작업법을 정리한다.

핵심은 모델에게 더 자세한 명령을 주는 것이 아니라, 모델이 더 멀리 갈 수 있게 하되
사용자가 방향, 근거, 책임을 잃지 않도록 하네스를 설계하는 것이다.

## 핵심 관점

### Capability overhang

`capability overhang`은 모델 안에는 이미 더 높은 능력이 있는데, 현재 하네스가 그 능력을
충분히 끌어내지 못하는 상태다.

여기서 하네스는 모델을 둘러싼 실행 환경이다.

- 시스템 프롬프트
- 사용 가능한 도구
- 컨텍스트 제공 방식
- 계획, 실행, 검증 루프
- 권한 정책
- UI와 제품 인터페이스
- 모델에게 허용된 자율성

모델이 강해질수록 하네스는 모델을 더 작게 만드는 울타리가 아니라, 모델이 넓게 움직이되
검증 가능하게 만드는 작업장이어야 한다.

### Unknowns

강한 모델에서 병목은 모델이 답을 못 내는 것이 아니라, 사용자가 자신의 unknown을 충분히
드러내지 못하는 데서 온다.

- `Known knowns`: 이미 프롬프트에 명시한 것
- `Known unknowns`: 내가 모른다는 것을 아는 질문
- `Unknown knowns`: 너무 당연해서 안 썼지만 보면 알아차리는 지식
- `Unknown unknowns`: 고려조차 못 한 것

unknown 찾기는 정답을 만들기 전에 문제 자체의 빈칸을 찾는 단계다.

## 8단계 작업법

### 1. Blind Spot Pass

작업을 시작하기 전에 모델에게 내가 놓치고 있는 unknown을 찾게 한다.

```text
이 작업을 시작하기 전에 blind spot pass를 해줘.
내 요구사항에서 빠진 결정, 애매한 용어, 숨은 의존성,
기존 시스템과 충돌할 수 있는 부분,
나중에 되돌리기 어려운 선택을 찾아줘.
그다음 구현 전에 나에게 물어봐야 할 질문을 중요도순으로 정리해줘.
```

목적은 모델을 바로 실행시키는 것이 아니라, 실행 전에 문제의 빈칸을 드러내는 것이다.

### 2. Brainstorms and Prototypes

말로는 설명하기 어렵지만 보면 판단할 수 있는 영역에서는 여러 방향의 시안을 만들게 한다.

```text
이 데이터셋으로 대시보드를 만들고 싶은데,
내가 시각 디자인 감각이 부족해서 어떤 방향이 가능한지 잘 모르겠다.

서로 완전히 다른 HTML 프로토타입 4개를 만들어줘.
각각 정보 밀도, 탐색 방식, 시각적 강조점이 다르게 해줘.
내가 보고 피드백할 수 있게 해줘.
아직 최종 구현으로 들어가지는 마.
```

이 단계는 주로 `unknown knowns`에 대응한다. 사용자는 말로는 못 해도 결과를 보면
무엇이 맞고 틀린지 판단할 수 있다.

### 3. Interviews

남은 모호함은 모델이 한 번에 하나씩 질문해서 확정하게 한다.

```text
이 프로젝트의 애매한 부분을 나에게 한 번에 하나씩 인터뷰해줘.
내 답이 아키텍처, 데이터 모델, 사용자 흐름, 권한 정책에 영향을 주는 질문을 우선해줘.
각 질문마다 네 추천 답도 같이 제시해줘.
```

좋은 인터뷰는 궁금한 것을 모두 묻는 것이 아니라, 나중에 바꾸기 어려운 결정부터 묻는다.

### 4. References

설명을 길게 쓰기보다, 모델이 따라야 할 실제 사례나 원본을 제공한다.

```text
vendor/rate-limiter에 있는 Rust 구현이 내가 원하는 backoff 동작과 정확히 같다.
그 코드를 읽고 의미를 설명한 뒤,
같은 semantics를 TypeScript API client에 구현해줘.
테스트도 원래 동작 기준으로 맞춰줘.
```

가장 좋은 reference는 작동하는 source code다. reference는 영감이 아니라 판단 기준이다.

### 5. Implementation Plans

바로 구현하지 말고, 바뀌기 쉬운 결정들을 중심으로 구현 계획을 만들게 한다.

```text
아직 구현하지 말고 implementation plan을 먼저 작성해줘.

특히 내가 나중에 조정할 가능성이 큰 부분에 집중해줘:
데이터 모델 변경, 타입/interface, 사용자 흐름, 권한 규칙,
외부 API 경계, 테스트 범위.

각 결정마다 추천안, 대안, 되돌리기 어려운 이유,
내가 확인해야 할 질문을 정리해줘.
```

이 단계는 구현을 늦추기 위한 문서가 아니라, 틀리면 비싼 결정을 미리 드러내는 장치다.

### 6. Implementation Notes

구현 중 새로 발견한 edge case, 계획에서 벗어난 결정, 모델의 보수적 선택을 기록하게 한다.

```text
구현하면서 implementation-notes.md를 유지해줘.

다음 내용을 기록해:
- 원래 계획에서 벗어난 결정
- 새로 발견한 edge case
- 보수적으로 선택한 부분
- 나중에 내가 검토해야 할 질문
- 테스트로 확인한 것과 확인하지 못한 것

edge case 때문에 계획에서 벗어나야 하면,
가장 보수적인 선택을 하고,
Deviations 섹션에 이유를 남긴 뒤 계속 진행해줘.
```

목적은 모델의 즉흥 판단을 투명하게 만드는 것이다.

### 7. Pitches and Explainers

구현이 끝난 뒤 결과물을 다른 사람이 판단하고 피드백할 수 있는 형태로 묶는다.

```text
프로토타입, 스펙, implementation notes를 하나의 설명 문서로 묶어줘.
팀 Slack에 공유할 수 있게 핵심 의사결정, 데모, 남은 리스크, 다음 액션을 포함해줘.
```

이 단계는 결과를 설명 가능한 상태로 만드는 팀 커뮤니케이션 하네스다.

### 8. Quizzes

마지막으로 사용자가 변경 내용을 책임질 수 있을 만큼 이해했는지 확인한다.

```text
이번 변경을 이해하기 위한 HTML report를 만들어줘.
무엇이 바뀌었는지, 왜 그렇게 했는지, 중요한 코드 경로, 테스트 결과를 설명하고,
마지막에 내가 풀어야 할 quiz를 넣어줘.
내가 quiz를 통과하기 전에는 merge 준비가 끝났다고 보지 마.
```

AI가 만든 결과라도 최종 책임은 사용자에게 있다. quiz는 그 책임을 감당할 만큼 이해했는지
확인하는 장치다.

## 스킬 설계에 적용하기

### seed-body

`seed-body`는 실전형 blind spot 프롬프팅에 가깝다.

목적은 사용자 발화에서 Essential 몸체를 수확하는 것이다. 따라서 4분류를 길게 설명하기보다
v1 성립에 필요한 빈 슬롯을 찾아 한 질문씩 회전하는 방식이 맞다.

```text
지금까지 나온 서비스 설명에서 v1을 확정하기 전에 비어 있는 슬롯을 찾아줘.
특히 역방향/예외 흐름, 행위자 충돌, 판정 가능한 기대 결과, 위험한 외부 접점을 봐줘.
단, 추측으로 확정하지 말고 가장 중요한 질문 하나만 물어봐.
```

### make-body

`make-body`는 일반 unknown 4분류보다 evidence 중심 4분류가 맞다.

- `Code-observed`: 코드가 직접 증명하는 실행 사실
- `Code-gap`: 코드만으로는 구분, 정책, 의도를 확정할 수 없는 빈칸
- `Conflict`: 코드, 이름, 흐름, 기존 문서가 충돌하는 지점
- `Human-confirm-needed`: 코드가 암시하지만 Essential 의미로는 사람 확인이 필요한 것

```text
이 변경 범위에서 unknown pass를 해줘.
각 항목을 Code-observed, Code-gap, Conflict, Human-confirm-needed로 분류해줘.
코드가 직접 지지하지 않는 정책/권한/생명주기/결과는 후보로 확정하지 말고 gap이나 conflict로 남겨줘.
System 사실과 Essential 의미를 섞지 말고, Essential은 인간 확인이 필요한 질문으로 정리해줘.
```

### grill-me

`grill-me`는 interview 단계에 해당한다. 더 정확히는 이미 나온 계획이나 설계를 압박해서
숨은 결정과 의존성을 드러내는 스킬이다.

```text
이 계획을 grill-me 방식으로 검증해줘.
결정 트리를 따라가며 숨은 전제, 빠진 선택지, 되돌리기 어려운 결정,
서로 의존된 결정을 하나씩 밝혀줘.
질문은 한 번에 하나만 하고, 각 질문마다 네 추천 답도 같이 제시해줘.
```

`seed-body`와 `grill-me`는 합치기보다 독립시키는 편이 낫다. 필요하면 다음 순서로 수동 사용한다.

```text
1. seed-body로 v1 Essential 초안 형성
2. grill-me로 초안 압박 검증
3. 나온 수정점은 seed-body 규칙으로 사용자 비준 후 반영
```

## 최종 요약

이 8단계는 점점 똑똑해지는 모델을 억누르는 방법이 아니다. 강한 모델이 더 멀리 갈 수 있게
하면서도, 사용자가 방향, 근거, 검증, 책임을 잃지 않게 하는 작업법이다.

예전 모델의 병목은 모델이 못 알아듣고, 코드를 못 짜고, 긴 작업을 못 버티는 것이었다.
강한 모델의 병목은 사용자가 문제를 덜 정의하고, 모르는 전제를 밝히지 못하고, 모델이 너무
멀리 가버린 뒤 결과를 충분히 이해하지 못하는 데 있다.

따라서 좋은 하네스는 모델을 제한하는 장치가 아니라, 모델의 자율성을 검증 가능한 작업 흐름
안에 넣는 장치다.
